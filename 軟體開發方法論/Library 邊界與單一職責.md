# Library 邊界與單一職責

## 故事從一個簡單的寄信函式開始

團隊有一個共用的寄信 library，介面大致是：

```java
sendEmail(String userId, String templateId, Map<String, Object> keyValues)
```

呼叫端提供使用者 ID、範本 ID 與範本欄位。Library 查出 `User.email`，把 `keyValues` 填入範本，再寄到使用者信箱。它原本只處理「如何產生並寄出一封信」。

某天，客戶 A 要求每封信的內容末尾附上 HMAC 簽章，讓收件方能用共享密鑰檢查內容是否遭到修改。原作者沒有斷言這個要求一定能提升安全性；案例關心的是需求應該放在哪一層。

負責的工程師發現：客戶 A 的使用者目前都落在某個 `UserCategory`，而這個分類目前只有客戶 A 使用。於是工程師在共用的 `sendEmail()` 裡加入判斷：

```text
if (user.category == A) {
    emailContent += hmac(emailContent);
}
```

表面上改動很小，也能滿足眼前需求；但原作者否決了這個 PR。原因不是「程式裡不能有 `if`」，而是客戶 A 的政策被寫進本應共用的寄信流程。

## 為什麼這個 `if` 會成為問題？

原貼文用三個判準說明好的 library：

1. **只看 API，大致能預期它會做什麼。** `sendEmail()` 看起來是寄信，不會讓呼叫端預期某個使用者分類會自動附上簽章。
2. **讀懂文件後，不應出現沒被說明的意外行為。** Library 的行為要能從契約理解，而非只有讀到某段分類判斷才能發現。
3. **功能應有單一職責，不持有特定客戶的業務規則。** 寄信機制要回答「怎麼寄」，客戶政策要回答「誰需要額外處理」。

第一、二點是對 API 可理解性的期待，不代表所有實作細節都必須寫進函式名稱；真正的問題是隱藏的業務規則改變了輸出。

把分類當成客戶身分的替代品，還會產生**目前成立、未來未必成立**的假設：假如新客戶加入同一個 `UserCategory`，新客戶的信也會被加上看不懂的簽章。這段邏輯不在客戶設定或呼叫端，後續接手的人更難發現。

原文再舉兩個可能出現的需求：客戶 B 要求信件密件副本送到指定信箱；客戶 C 有多個收件地址，要求每個地址各寄一封，而不是一封信同時寄給所有地址。如果每來一個客戶就往 `sendEmail()` 增加一個 `if`，共用流程會逐漸變成客戶政策的集合。**今天判斷正確，不等於放在這裡對未來也合適。**

## 原作者的方案：讓呼叫端提供內容後處理器

對「寄出前修改信件內容」這個需求，原作者提議給 `sendEmail()` 增加可選的 `PostProcessor` 參數，由應用層決定是否提供實作：

```java
interface PostProcessor {
    String process(String emailContent);
}

// sendEmail() 產生內容後、寄出前
if (postProcessor != null) {
    emailContent = postProcessor.process(emailContent);
}
```

一般呼叫端不提供處理器，保留原來的寄信行為；客戶 A 的應用流程提供 HMAC 處理器。決定「客戶 A 要簽章」的是應用層，不再由 library 查使用者分類來決定。將來若簽章演算法從 HMAC-SHA-256 換成 HMAC-SHA-512，原作者主張只須替換應用層的處理器實作，不必再改共用 library 裡的客戶判斷。

這個設計把兩種**變更理由**分開：寄信流程改變時修改 library；客戶的內容處理政策改變時修改應用層。這也是原文藉單一職責原則（Single Responsibility Principle）強調的重點：不只要讓現在的程式能跑，還要考慮未來改動會牽動誰。

## 方案的適用範圍與注意事項

`PostProcessor` 適用於「寄出前轉換信件內容」，**不是**所有寄信需求的通用擴充點。客戶 B 的密件副本屬於收件者設定；客戶 C 的一對一寄送涉及寄送次數與流程。這些需求應在相應 API 或應用層處理，不能硬塞進只接收、回傳文字的處理器。

原貼文說，替換處理器後，共用 library 不用再改、也不用重測。較精確地說：**在原有契約不變時**，不必為演算法更換而修改 library 的客戶分支；新的處理器及它與寄信流程的整合仍要測試。首次新增可選參數也須確認 API 相容性及既有呼叫端行為。

此外，HMAC 能否供收件方驗證，還取決於共享密鑰如何管理、簽章附在哪裡、雙方對原文與編碼的定義是否一致。這些是安全需求本身的設計，不會因為抽出 `PostProcessor` 就自動成立。

## 原文最後談的：AI 產碼與開發者的差別

原作者預期有人會說「AI 已經會寫程式，開發者不再需要了」，並用速食自動化生產線比喻：生產線能高效做出某種食物，不代表所有廚師都失業。相同地，能產出程式碼，不等於已完成整個軟體開發工作。

原文也預想另一種反駁：「現在 AI 的 context window 不夠大，未來模型變強就能做好系統架構。」作者沒有斷言未來不可能，而是說未來的事留待未來再談；目前真正想強調的差別，不是人類永遠寫碼比較快，而是開發者要判斷：需求該不該做、由哪一層負責、怎樣避免系統埋下難以維護的規則。對 Senior Developer 或 Tech Lead 而言，決定**不做什麼**，有時比動手 coding 更花時間，也更影響專案能否長期維護。

廚師之所以不只是一把刀或一條產線，是因為他們還要判斷料理與服務的整體結果。這是原文對「Software Developer」與只負責產出程式碼的「coder」所作的區分；它是作者的觀點，不是 AI 能力或就業趨勢的定論。
