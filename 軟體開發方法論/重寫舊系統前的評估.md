# 重寫舊系統前的評估

> 核心問題不是「舊系統有多難看」，而是「重寫能否用可承受的風險解決真正的問題」。以下案例均為原貼文作者虛構的情境，不是特定公司的事件或通用的效能數據。

## 先拆開「程式碼很爛」的不同意思

原文從工程師想重寫老系統談起。作者以一段曾經從約六萬行 PL/SQL 縮到約一千八百行程式碼、另有約五百行註解的經驗，說明大量程式碼**可能**有簡化空間；但行數本身既不能證明品質差，也不能證明重寫一定划算。

作者接著設計三種「看起來該重寫」的情境：

1. **難以理解的程式碼。** 一個 Spring Boot 專案大多數依賴寫在 `application.xml`，某個 class 卻偏用 `@Autowired`；刪除 XML 中看似無用的物件後，執行階段才出錯。這可能反映隱藏依賴或缺少測試，但應先釐清實際依賴關係；單憑風格不一致，還不足以判定必須重寫。
2. **跨語言的隱藏業務邏輯。** Go 專案裡某個 struct 欄位莫名變成 `valueX`，專案內也找不到賦值來源；追查才發現程式呼叫 C 程式庫，C 再透過指標改寫該欄位，而相關程式碼放著「沒用」的過時註解。搜尋 Go 程式碼找不到值從哪裡來，顯示系統行為不能只靠單一語言的原始碼理解。
3. **表面上可運作、實際上難以完成任務。** 作者用「花錢買回一款讓多人線上玩的 Monopoly 遊戲，卻連一局正常遊戲都玩不完」比喻：錯誤被大量 `exception` 吞掉，不等於功能真的正常。這時要先界定失敗的是哪些關鍵流程，而非只看有沒有當機。

先前成功簡化 PL/SQL 的經驗，不能取代對目前系統的評估。

## 問題可能不在程式碼，而在人與組織

原文稱這類阻力為「政治問題」，舉了三個情境：

- **荒謬規則背後可能有權責邊界。** 虛構的超市進口澳洲蘋果，系統卻要求附上奧地利出口文件。負責進出口的同事只說規則用了多年、不會錯。工程師不能因此認定程式碼可以直接刪掉；得找到制定規則的人、文件與實際流程，確認它究竟是錯誤、誤解，還是未寫進程式碼的業務要求。
- **資料庫遷移不只是技術選型。** 聊天訊息以 `(chatroom_id, timestamp)` 作為 MySQL 主鍵，資料量增長後遇到瓶頸。有人主張搬到 NoSQL，資料工程師卻極力反對；最後查出對方的資料管線只熟悉以 MySQL 為資料來源，不會接新的來源。爭議裡有資料管線、人力與交接成本，不能只比較資料庫功能。原文人物說「NoSQL 無法做 atomic transaction」屬於情境中的爭論，**不是普遍事實**；不同系統的交易能力與需求須分別確認。
- **局部最佳化可能是升遷誘因。** 有工程師主張把高延遲的 PHP endpoint 改寫成 Go，聲稱可降到 20 ms 以下、節省 70% 伺服器成本。但該 endpoint 只是前端在背景同步輸入，不影響主要操作；使用者沒抱怨過慢，模組成本占整體不到 5%。作者設定的真正動機是：小幅改善較容易作為升遷成果，也比修整整個系統省力。數字是虛構說法；即使局部效能真的提升，也應先量測對使用者、總成本及團隊目標的實際價值。

這些故事不表示異議者一定別有用心。重點是：找出技術症狀背後的需求、依賴、成本與決策權，才能判斷重寫能解決什麼。

## 決定重寫前，先回答三組問題

### 1. 現有系統能否透過重構改善？

「別人寫的程式很爛」不等於「程式真的無法修」。要判斷是否值得重寫，至少要能讀懂問題所在，並有能力在必要時寫出更易維護的程式。原文提醒：理解真正的爛程式、寫出好的替代方案，以及接受自己的寫法未必最優，都需要一段時間的一線經驗。

可先辨認最難維護的模組、最常出錯的流程，以及可否用測試保護後逐步拆解。這是整理原文觀點時補上的判斷方式，並非原文提供的固定流程。

### 2. 要一次切換，還是讓新舊系統並行？

- **一次切換：**先由新系統完整處理資料與流程，再把舊系統退場。若把未理解的舊規則和資料問題一併帶過去，可能只得到一個新的難維護系統；切換與回退的風險也集中。
- **漸進遷移與寬限期（grace period）：**先讓部分資料或功能由新系統處理，其他仍用舊系統；兩套系統暫時共存。原文用超市進貨作比喻：新進貨先只讓水果類走新系統，穩定後再擴大類別。這能縮小每次上線需測試的範圍，但**不保證**總風險較低：未理解的業務規則可能從舊系統滲入新系統，兩套系統也要同時維護。若沒有治理和舊系統退場條件，寬限期可能永遠不結束。

選擇遷移方式前，需要盤點資料與流程如何切分、新舊系統怎麼協作、如何驗證結果，以及何時能關閉舊系統。這些是從原文風險延伸的檢查點。

### 3. 你能推動跨部門的決定嗎？

重寫若牽涉業務規則、資料管線、維運流程，就不是工程師獨自能完成的技術決定。原文要讀者追問：碰到不合理的進出口規則，能否找負責同事釐清？受影響部門會合作嗎？主管是否支持？若提案不是自己發起，提出者的真正目標是什麼？

作者用一句話收束：**技術問題才能用技術解決；若把權責或利益衝突當成純技術問題，就算重寫完也可能繼承原本的困境。**

## AI 與提出重寫的理由

原作者認為 Staff Engineer 的工作，有很大一部分是 AI 難以代替的情境判斷：辨認同事說「不反對、不痛不癢」背後的態度，或聽懂有人說「東西很爛、要重寫」的真正理由。這是作者對工作性質的看法，並非 AI 能力的定論。

貼文最後提醒：若對外只說「PHP、Ruby 或 Node.js 很難維護，所以用新語言重寫」，卻不願坦白「我們先前的程式碼品質差到無法靠重構處理」，就得檢查自己說的是技術原因，還是在逃避檢討。**做一件事，需要一個經得起檢驗的理由。**
