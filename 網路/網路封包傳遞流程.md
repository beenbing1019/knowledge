# 網路封包傳遞流程

**術語**：HTTP＝超文字傳輸協定（Hypertext Transfer Protocol）；TCP＝傳輸控制協定（Transmission Control Protocol）；TLS＝傳輸層安全性協定（Transport Layer Security）；UDP＝使用者資料報協定（User Datagram Protocol）。

從手機打開網站時，資料不會直接跳到伺服器。它會經過本機網路、路由器與目的地網路。

1. **應用產生資料**：瀏覽器準備請求；作業系統加入 TCP 或 UDP 標頭，再封裝成 IP 封包。
2. **選下一站**：作業系統查路由表，選網路介面與下一跳。目的地不在本機網路時，通常交給預設閘道。
3. **在網路間轉送**：路由器查看目的 IP 位址，逐跳選路；每一跳的鏈路層封裝可能不同。
4. **目的端接收**：目的地網路把封包交給伺服器。作業系統依協定與埠號交給相應程序。

例如網站打不開時，可分段檢查：裝置是否連上 Wi-Fi、是否能到閘道、是否能到目的地網路，以及伺服器應用是否有回應。DNS 查詢與 NAT 也可能參與過程，但不是每段連線都必經同一種設備。

**IP 採盡力而為**，不保證封包一定送達。需要可靠、有序傳輸時，由 TCP 或應用層機制負責。

## 用網站連線逐段排查

假設瀏覽器要連 `example.com`：先透過網域名稱系統（DNS，Domain Name System）解析名稱取得網際網路協定（IP，Internet Protocol）位址，再查路由選下一跳；本機若不知道閘道的鏈路層位址，會先以 ARP（Address Resolution Protocol，IPv4）或鄰居探索（Neighbor Discovery，IPv6）取得。路由器每跳重新封裝鏈路層資料，原始目的 IP 通常不變；NAT（Network Address Translation）環境則可能改寫位址與埠。

- 名稱解析失敗：檢查 DNS；換 IP 測試有助於分辨解析與連通問題。
- 網路層不可達：查本機路由、閘道與中間防火牆；不能只看網站程式日誌。
- TCP 已連上但網頁仍錯誤：檢查 TLS、HTTP 與應用回應，網路可達不代表服務可用。

參考：[RFC 791：Internet Protocol](https://www.rfc-editor.org/rfc/rfc791)、[MDN：How the web works](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works)。
