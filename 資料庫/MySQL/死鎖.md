# 死鎖

**術語**：SQL＝結構化查詢語言（Structured Query Language）。

**問題**：兩筆轉帳同時要更新帳戶 A、B。交易 1 先鎖 A 等 B；交易 2 先鎖 B 等 A。雙方互等，誰都無法繼續，這就是死鎖（Deadlock）。

**原因與影響**：取得多個鎖的順序不同，加上交易長時間持鎖，增加相互等待機會。InnoDB 偵測到死鎖時，通常會回滾其中一筆交易；應用可能收到失敗訊息。

**降低與處理**：

1. 所有轉帳都依固定順序更新帳戶，例如先鎖編號較小者。
2. 縮短交易，不要在持鎖期間等待外部應用程式介面（API，Application Programming Interface）；檢查查詢索引以縮小鎖定範圍。
3. 辨識死鎖錯誤，**重試整筆交易**，而非只重試失敗的 SQL。重試要有限次並避免重複外部副作用。
4. 查死鎖日誌與鎖等待，找出衝突的語句與持鎖時間。

換成 `READ COMMITTED` 或開啟交易，都不能保證沒有死鎖。**鎖等待逾時不等於死鎖**：InnoDB 預設可能只回滾逾時語句，應用需明確決定回滾整筆交易。

## 重試不是唯一解

兩位顧客同時轉帳 A、B，若交易固定按帳戶編號鎖定，可降低互等；但其他 SQL 仍可能形成死鎖。應用須捕捉對應錯誤，有限次重試**整筆**交易；若先呼叫外部付款服務再重試，必須使用冪等鍵避免重複扣款。

可選縮短交易、固定鎖順序、改善索引縮小鎖範圍，或對可重試的衝突加退避。調低隔離層級可能改變其他讀寫保證，不能當成無代價的死鎖開關。

參考：[MySQL 8.4：Deadlocks in InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)。
