# 大量資料查詢與擴充

**問題**：訂單表成長後，查一位顧客最近的訂單從幾毫秒變成幾秒。先找慢在哪裡，不要因為資料達到某個筆數就直接分片。

## 由小到大處理

1. **量測**：記錄慢查詢、執行時間、頻率及資料量；用 `EXPLAIN` 查看掃描、索引、排序與關聯。
2. **改善查詢**：依常用的過濾與排序條件建索引；只取必要欄位，避免一次讀取過多列。索引也會增加寫入與儲存成本。
3. **減少重複工作**：若結果可容忍短暫過期，可快取熱門查詢，並設計更新與失效。對按時間查詢的表，只有能利用分區裁剪時，分區才可能減少掃描範圍。
4. **檢查資源**：量測記憶體、儲存、CPU 與連線數，再決定是否升級硬體或分攤讀取。
5. **最後評估分片**：單機調整後仍無法滿足需求，再考慮分散到多台資料庫；跨分片查詢、交易與維運會更難。

例如查「某顧客最近 20 筆訂單」，可先檢查 `(customer_id, created_at)` 複合索引與查詢計畫。分片不是「一億筆資料」的固定答案。每次改一項因素，比較調整前後延遲及負載。
