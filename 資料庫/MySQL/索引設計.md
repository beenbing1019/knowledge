# 索引設計

索引像書末目錄：能減少查詢掃描，但每次新增或更新資料也要維護目錄。因此索引應為**常用查詢**服務，不是每個欄位都加一個。

1. 找出常用、耗時的查詢，確認過濾、關聯及排序條件。
2. 用 `EXPLAIN` 查看掃描範圍與現有索引是否被使用。
3. 視條件設計複合索引。例如依顧客查最近訂單，可考慮 `(customer_id, created_at)`；順序會影響索引可用性。
4. 衡量索引大小、寫入成本與資料分布；新增後量測效益，移除無用或重複索引須先確認其他查詢沒有依賴。

InnoDB 一般索引採 B-tree，不能直接改建成使用者管理的 Hash 索引。定期重建索引也不是所有慢查詢的通用解法。先量測瓶頸，再動手。

## 對同一資料表選索引

- 顧客最近訂單：`WHERE customer_id = ? ORDER BY created_at DESC` 可先考慮 `(customer_id, created_at)`，再用 `EXPLAIN` 確認使用情況。
- 只查日期區間：若以 `created_at` 起頭的查詢很常見，前述複合索引未必能像單獨以日期起頭的索引那樣縮小範圍；另加索引則要付出寫入與空間成本。
- 查極少數值且回傳大量列：優化器可能選全表掃描；不要把「沒走索引」直接判為錯誤。

可選複合索引、調整查詢，或在資料量小時維持全表掃描；依查詢計畫與實際延遲決定。

**覆蓋索引（Covering Index）**：若查詢所需欄位都能由同一索引提供，資料庫可能不必再讀取資料列。例如只查 `customer_id` 與 `created_at`，可檢查 `(customer_id, created_at)` 是否覆蓋查詢；若改用 `SELECT *`，其他欄位不在索引裡，就失去這項好處。不要為了覆蓋所有查詢把整張表的欄位全加進索引；索引變大，也會增加寫入成本。用 `EXPLAIN` 與實測確認。

參考：[MySQL 8.4：Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)、[How MySQL Uses Indexes](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)。
