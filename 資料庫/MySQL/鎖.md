# 鎖

多筆交易同時修改資料時，InnoDB 會用鎖控制衝突。但一般 `SELECT` 的快照讀取**不會一律因行排他鎖而等待**。

- **共享鎖**：允許相容的共享讀取。例如 `SELECT * FROM accounts WHERE id = 1 FOR SHARE;`。
- **排他鎖**：寫入或 `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;` 取得；衝突的鎖定讀取與寫入要等待。
- **記錄鎖、間隙鎖、next-key lock**：依索引、範圍條件及隔離層級決定。查一段日期，可能鎖住不只一筆資料。
- **明確表鎖**：`LOCK TABLES accounts WRITE;` 與 `UNLOCK TABLES;`。`LOCK TABLES` 可能隱含提交，不能與 InnoDB 交易內的鎖混用概念。

例如庫存更新卡住，先查是否有長交易持鎖，再檢查更新條件是否使用合適索引。縮短交易與鎖定範圍可減少等待，但仍須處理死鎖。

參考：[MySQL 8.4：InnoDB Locking](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)、[LOCK TABLES](https://dev.mysql.com/doc/refman/8.4/en/lock-tables.html)。

## 查庫存卡住的處理順序

1. 先查是哪筆交易持鎖、等待了多久，別直接把所有查詢都加上 `FOR UPDATE`。
2. 確認更新條件與索引：沒有合適索引時，掃描及鎖定範圍可能比想像大。
3. 可縮短交易、調整索引與鎖順序；若選條件式原子 `UPDATE` 取代「先讀再鎖」，也要檢查受影響列數。

一般快照讀取與鎖定讀取取得的資料和等待行為不同；選擇取決於是否要保護後續寫入，而非「查詢一定要鎖」的口訣。
