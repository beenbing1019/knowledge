# Redis 效能最佳化

**問題**：促銷開始時，商品頁讀取變慢。先找瓶頸是網路往返、慢命令、記憶體、快取未命中，還是後端資料庫，不能只靠增加節點。

1. **量測**：看請求延遲、命令速率、`INFO`、`SLOWLOG` 與快取命中率。確認是否有大鍵或單次處理過多資料。
2. **選資料型別**：計數器可用字串與 `INCR`；排行榜可用有序集合。依操作需求選，不要只看節省多少位元組。
3. **減少往返**：批次命令與管線化（pipelining）可減少網路往返；管線化**不保證**整批命令具有交易原子性。
4. **管好快取生命週期**：設定合理的存活時間（TTL，Time To Live），處理更新與失效，並避免大量熱門鍵同時到期。
5. **確認容量**：單機確實到瓶頸後，再評估 Redis Cluster 分片；它會增加跨槽操作與維運成本。持久化選項是資料恢復與成本取捨，不是通用加速開關。

例如促銷頁要讀取多件商品，先量測是逐筆網路請求太多，還是商品快取同時失效。前者可評估管線化；後者須處理到期抖動與回源限流。改動後比較延遲與負載。

## 同一個慢頁面，三個瓶頸

- 讀十個商品各發一次請求：可用管線化減少往返；若資料可一次取，改資料模型或批次命令也可能更好。需檢查批量命令對單次執行時間的影響。
- 熱門商品剛過期，同時湧入大量請求：單次重建、短暫舊值或回源限流，比只加大 Redis 記憶體更對症。
- Redis 記憶體滿且持續淘汰：先看鍵分布與 TTL，必要時擴容或分片；管線化不能增加容量。

優化後量測尾端延遲、命中率與資料庫負載，不只看單次平均耗時。

參考：[Redis 官方：Pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/)。
