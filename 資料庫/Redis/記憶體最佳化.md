# Redis 記憶體最佳化

**問題**：商品快取的鍵越來越多，Redis 接近記憶體上限，寫入開始失敗或熱門資料被淘汰。

1. 用 `INFO memory` 看總量，抽樣用 `MEMORY USAGE key`、`OBJECT ENCODING key` 看大鍵與編碼。
2. 依實際資料選字串、雜湊（Hash）、集合（Set）或有序集合（Sorted Set）。過多細碎鍵有額外管理成本，但也不要把所有資料硬塞進單一大鍵。
3. 讓短期資料設定合理存活時間（TTL，Time To Live）。過短會增加未命中，同時到期會造成回源尖峰。
4. Redis 7 起，小型 Hash／Sorted Set 可採緊湊的 **listpack**。
   相關門檻如 `hash-max-listpack-entries`、`hash-max-listpack-value`、`zset-max-listpack-*`。
   舊版 `*-max-ziplist-*` 不宜直接套到新版；List 使用 quicklist／listpack。
5. 量測後再設 `maxmemory` 與淘汰策略，並預留持久化和複製時所需的額外空間。

例如大量短期驗證碼沒有設定 TTL，會一直占用記憶體；依業務有效期設到期時間，比盲目調整編碼更直接。RDB／AOF 用於故障恢復，`appendfsync` 不是釋放鍵值記憶體的工具。

參考：[Redis 官方：Memory optimization](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)。
