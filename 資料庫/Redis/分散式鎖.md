# Redis 分散式鎖

**問題**：兩位工作者同時產生同一份報表，浪費資源，甚至同時改寫結果。需要協調「目前由誰處理」。

在**單一 Redis 節點**取得帶租約的鎖，可用同一個原子命令：

```text
SET lock:resource <唯一持有者識別> NX PX <租約毫秒數>
```

`NX` 表示鍵不存在才設定；`PX` 設定毫秒到期時間。分開執行 `SETNX` 和設定到期時間，可能在中間當機，留下不會過期的鎖。釋放時要以原子操作檢查值仍是自己的識別，再刪除；不能直接 `DEL`，以免刪掉別人接手後的鎖。

**剩餘風險**：舊工作者可能停頓超過租約，醒來後仍繼續寫入；主節點故障時，尚未複製的鎖也可能消失。嚴格保護資料時，可用遞增的隔離權杖（fencing token）或下游資料庫條件更新，拒絕舊工作者的寫入。Redlock 也不是所有故障下的絕對保證。

參考：[Redis 官方：Distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

## 什麼情境該用哪種保護？

- 重複產生報表只是多花運算資源：單節點租約鎖可減少重複工作，仍要容忍偶發重跑。
- 同一份帳務不能被舊工作者覆寫：僅靠租約不夠；可用下游資料庫的版本號條件更新，或遞增的 fencing token 拒絕過期持有者。
- 要確保同一筆訂單只寫入一次：優先用資料庫唯一約束與冪等鍵；鎖故障或逾期後，約束仍可保護資料。

鎖的安全性必須和它所保護的資料一起驗證，不能把「拿到鎖」當作寫入一定安全。
